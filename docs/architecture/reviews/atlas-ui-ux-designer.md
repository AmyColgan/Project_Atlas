# Atlas UI/UX Designer — Review

Scope per `.claude/agents/atlas-ui-ux-designer.md`: new-game flow (screen sequence from launch to first turn), the civilization-selection **experience** (screens/interaction, not the underlying data structure — that is `atlas-civilization-designer`'s territory, running in parallel), and how the existing HUD (`TopBar`, `InspectorPanel`) needs to evolve once the map renders in 3D. Research/design only — no file under `src/` was touched; every recommendation below is checked against the actual shipped code (`src/ui/App.tsx`, `src/ui/WorldCanvasView.tsx`, `src/ui/HUD/TopBar.tsx`, `src/ui/HUD/InspectorPanel.tsx`, `src/ui/state/simulationStore.ts`, `tailwind.config.js`) rather than assumed.

I read `atlas-game-director.md` and `atlas-3d-architect.md` (both already committed to `docs/architecture/reviews/` when I started) and `atlas-world-designer.md`. `atlas-civilization-designer.md` did not exist yet at write time — it runs in parallel and I have not seen its output. Everywhere this review touches civilization data, I describe what the *screen* needs from that data, not what the data's shape should be.

## New-Game Flow Proposal

Confirmed directly in `src/ui/App.tsx`: the current build renders `TopBar` + `WorldCanvasView` + `InspectorPanel` with no setup screen at all — `useSimulationStore`'s initial state is `world: createTestWorld(1)`, i.e. the app boots straight into an already-generated world. This matches the game-director's Finding 4 exactly: new-game flow is greenfield implementation of `docs/specifications/mvp_specification.md` §3, not a redesign of an existing flow. I am scoping strictly to that spec's four steps, per the game-director's Recommendation 3, and calling out anywhere I'd be tempted to add a step.

**Proposed screen sequence (each screen is a full-bleed overlay that replaces, not layers under, the HUD shell until the last step):**

1. **Title / Continue screen.** Not in `mvp_specification.md` §3, but required by existing functionality: `TopBar` already has `Load` wired to `loadFromLocalStorage()` in `simulationStore.ts`. Without a title screen, "load a save" and "start new game" have nowhere to live before the HUD exists. Proposed as the minimal addition needed to make the existing save/load feature reachable, not new scope — flagging it as an addition beyond spec §3, per the game-director's instruction to surface additions explicitly rather than fold them in silently.
2. **Civilization Count screen** (§3 step 1): a single slider/stepper, 4–8, default 5, large enough touch/click targets, no other content. Simplest possible screen — resist decorating it, it exists only to set N before step 3 needs to render N slots.
3. **Civilization Selection/Generation screen** (§3 step 2): see "Civilization-Selection Experience" below — this is the heaviest screen in the flow.
4. **Leader Identity Selection screen** (§3 step 3): player enters a name and picks exactly 2 traits from a fixed trait list (data source: `atlas-civilization-designer`'s trait vocabulary — I don't own the list contents, only its presentation as a card-grid with single/double-select state and a running count of "2/2 selected"). AI opponents' full procedural profiles are generated silently here (no player-facing screen — nothing in §3 asks the player to review AI leader profiles before the game starts).
5. **World Seed screen** (§3 step 4): a text input for a custom integer seed plus a "Randomize" button (visually consistent with `TopBar`'s existing "New World" button, which already calls `regenerate(Math.floor(Math.random() * 1_000_000))` — same interaction pattern, different screen).
6. **Handoff into `App.tsx`.** The setup flow's final action calls the equivalent of today's `regenerate(seed)` but parameterized with civ count/selections/leader identity (a store action that does not exist yet — `regenerate` currently only takes a seed and reuses `createTestWorld`'s single hardcoded faction). This is a `simulationStore.ts` surface change I'm flagging as needed, not one I'm designing the internals of — it depends on `atlas-civilization-designer`'s data shape and `atlas-world-designer`'s N-faction homeland placement (both in flight). Once dispatched, the setup overlay unmounts and `App.tsx`'s existing `TopBar`/`WorldCanvasView`/`InspectorPanel` tree renders unchanged — **no changes proposed to `App.tsx`'s structure itself**, only to what mounts before it.

**Explicitly not proposed** (would be scope creep against §3, flagging per the game-director's Recommendation 3 rather than silently adding): difficulty selection, map size, victory-condition toggles, homeland/starting-position picking. On the last one specifically: `atlas-world-designer`'s review (Open Question 5) asks whether homeland choice is ever player-facing. Per `mvp_specification.md` §3, which lists exactly four steps and none of them is geography, my answer is **no** — homeland placement stays fully automatic and the flow above has no step for it. If the Project Director wants to add one, it would insert between steps 3 and 4 above and would need a map-preview widget that doesn't exist yet anywhere in `src/ui/`.

## Civilization-Selection Experience

This is the screen most likely to overlap with `atlas-civilization-designer`'s output — the game-director's review already flagged that both our role descriptions contain the literal phrase "civilization selection" (Contradictions §1). My position, stated plainly per the ground rules: **I own the screen layout, card/grid presentation, preview interaction, and confirm/back controls. `atlas-civilization-designer` owns what fields exist on a preset and on a custom civilization, and the default preset roster's content.** Everything below describes UI given *some* data shape with these fields — name, primary color, faction trait, (later) emblem — without asserting that shape is final.

**Proposed layout — two-mode toggle at the top of one screen, not two separate screens:**

- **Preset mode (default tab).** A responsive grid of civilization cards — swatch of the primary map color, name, faction trait with its numeric effect (e.g. "Agrarian — +10% Food yield", per §3's own example), and (once available) an emblem/flag placeholder resolved through `AssetManager` exactly like `terrain.plains` is today — **no hardcoded `<img>` or inline SVG per civilization**, matching the "no hardcoded graphics" discipline already established in `assetManifest.ts`. Clicking a card selects it (visually: accent-colored border using the existing `atlas-accent` token, consistent with hover states already used in `TopBar.tsx`); a confirm button advances. N cards must render (one per civ count chosen in the prior screen), so the grid needs a determinate max (per `mvp_specification.md` §3, N ≤ 8) — an 8-card grid is the layout's ceiling case to design against, not 4.
- **Custom mode (second tab, same screen).** A form: name field, color picker (constrained to a palette the renderer can key against — arbitrary RGB risks clashing with the accent/warm/border tokens already fixed in `tailwind.config.js`; recommend a curated swatch list, not a raw color wheel), faction-trait single-select from the same trait list presets draw from, and — pending `atlas-civilization-designer`'s data structure — whatever government-type/interest-group inputs their proposal adds. I am not proposing the contents of that picker, only that a picker-shaped slot exists in the layout for it.
- **Live preview panel**, persistent across both tabs: shows the selected/constructed civilization's card as it will appear in-game (same visual treatment InspectorPanel gives faction territory today — `style={{ color: faction.color }}` pattern in `InspectorPanel.tsx` line 32 is the existing precedent for civ-color-driven UI and should be reused here, not reinvented).
- **Repeat-or-batch for N>1:** since §3 has the player pick *their own* civilization only (AI opponents are procedurally assigned, per step 2's "Procedural Generation assigns..." language, which reads as automatic for AI slots) — this screen is single-selection for the player's own civ, not a loop over N cards to fill. The remaining N-1 slots are filled silently by the same procedural generation AI leaders get, with no per-slot player review screen. This keeps the screen count flat regardless of N, and avoids an N-iteration wizard that isn't in the spec.

## HUD Evolution for 3D

Grounded in `atlas-3d-architect`'s review: the `WorldRenderer` interface (`init`, `resize`, `renderFrame`, `hexAtScreenPoint`, `destroy`) stays unchanged, and the one proposed addition is optional `CameraState` fields (`tiltDeg?`, `orbitDeg?`, `heightZ?`) that `CanvasWorldRenderer` simply ignores. That constrains what the HUD actually needs to change — it is not a full redesign.

- **`TopBar.tsx`: no structural change needed.** It reads `world.turn`, `seed`, and dispatches `regenerate`/`saveGame`/`loadGame` — none of that is renderer-aware today and none of it needs to become renderer-aware for a 3D swap. Its buttons are plain Tailwind-token-styled elements (`atlas-panelBorder`, `atlas-accent`, etc.) with no canvas/2D assumptions baked in, so it survives a `WebGLWorldRenderer` swap untouched.
- **`WorldCanvasView.tsx`: the pointer-handling layer needs new input affordances, not a rewrite.** Today `handlePointerMove`/`handleWheel` map directly to `panBy`/`zoomBy` on a 2D `{x, y, zoom}` camera. If `atlas-3d-architect`'s optional `tiltDeg?`/`orbitDeg?` fields ship, the HUD needs *some* control surface to drive them, since a mouse-drag-to-pan gesture doesn't naturally disambiguate "pan" from "orbit." Proposed: a modifier-gated gesture (e.g., right-click-drag or a held key + drag) for orbit/tilt, layered onto the existing `onPointerDown/Move/Up` handlers already in `WorldCanvasView.tsx` — same event plumbing, new branch, not new component. This should be treated as additive to the existing pointer handlers, not a replacement of the pan/zoom interaction model that already feels tuned (`LERP_SPEED`, `CLICK_DRAG_THRESHOLD_PX` in the current code represent real interaction-feel tuning that a 3D swap should not discard).
- **New HUD affordance: a compact camera-reset/orbit-indicator control.** Once tilt/orbit exist, players need a visible way to know the camera isn't in its default top-down-equivalent orientation and a one-click way to get back to it (a small icon button near the existing `TopBar` action cluster, or a floating control docked opposite `InspectorPanel` — bottom-right, mirroring `InspectorPanel`'s existing bottom-left placement so the two don't compete for the same corner). This is new UI surface, not present in Milestone 1, and should be called out as an addition rather than assumed to fall out of the interface change for free.
- **`InspectorPanel.tsx`: layout survives, one addition to consider.** Its content (terrain, territory, city name/population/capital flag) is renderer-agnostic — it reads `world.map`/`world.cities`/`world.factions`, never the renderer. It does not need to change for 3D. The one thing worth flagging: `hexAtScreenPoint` becomes a raycast in 3D (per `atlas-3d-architect`'s review) instead of O(1) algebra — functionally invisible to `InspectorPanel`, but if raycasting ever introduces perceptible hover latency, that's a reason to consider a hover-debounce, not a panel redesign.
- **GDD §8C ("customized, styled HUD matching the civilization's identity") is not yet implemented anywhere and is orthogonal to 3D.** Today's HUD is a single fixed dark theme (`tailwind.config.js`'s `atlas.*` tokens) with no civilization-driven theming hook. This applies whether the renderer is 2D or 3D and is really a new-game-flow/civilization-selection consequence (once a civ has a color, `TopBar`/`InspectorPanel` accents could switch to it) rather than a 3D-specific requirement — flagging so it isn't lost, but it does not block or get blocked by the 3D work.
- **What does *not* need to change:** no HUD component needs to become 3D-aware in the sense of importing anything from `graphics/`. The existing boundary — HUD reads the Zustand store, `WorldCanvasView` alone owns the renderer instance and imperative loop — is exactly the seam `atlas-3d-architect`'s recommendation preserves, and none of my proposals cross it.

## Contradictions or Disagreements Found

1. **Confirmed overlap, not yet a real conflict, with `atlas-civilization-designer`** (per game-director's Contradictions §1, which predicted this before either of our files existed): both role descriptions say "civilization selection." I have stated my assumption plainly above — I own the screen/interaction/visual layout, they own the data shape and preset roster content. Since their file wasn't written when I finished, I cannot confirm they've made the same split; the Project Director should verify both files agree on this boundary before either is implemented.
2. **No disagreement with `atlas-game-director`:** my new-game-flow proposal follows their Finding 4/Recommendation 3 exactly (scope to §3's four steps, call out additions explicitly). The one addition I introduced — a title/continue screen — is called out as exactly that, an addition, per their instruction.
3. **No disagreement with `atlas-3d-architect`:** my HUD proposal treats their optional `CameraState` extension as the trigger for new orbit/tilt controls, and explicitly does not ask for any `WorldRenderer` interface change beyond what they already proposed. I am, however, adding a concrete consequence they didn't cover: *if* `tiltDeg?/orbitDeg?` ship, a new HUD control (camera-reset affordance, orbit-gesture disambiguation) is required — this is new UI scope that should be counted alongside their vertical-slice estimate, not assumed to be free.
4. **Answers `atlas-world-designer`'s Open Question 5 directly:** they asked whether new-game flow ever exposes homeland/starting-position choice to the player. Per my reading of `mvp_specification.md` §3 (four steps, none geographic), my answer is no — see New-Game Flow Proposal above. If the Project Director disagrees, it changes both their candidate-pool design and adds a screen to my proposed flow.
5. **Unconfirmed dependency, not a contradiction:** my new-game-flow handoff (item 6 above) assumes `simulationStore.ts` gains a new action to instantiate N factions with player selections, replacing today's single-faction `regenerate(seed)`. This depends on both `atlas-civilization-designer`'s data shape and `atlas-world-designer`'s N-faction homeland-placement algorithm landing first — I am flagging the store-action surface as needed, not designing its internals, since both dependencies were in-flight and unseen while I wrote this.

# Atlas Game Director — Review

Scope per `.claude/agents/atlas-game-director.md`: 3D-conversion/vertical-slice scope honesty, new-game-flow/civ-selection coherence, campaign-biography integration with the leader-profile system, and cross-specialist contradiction surfacing. This review does not evaluate rendering technology choice, world-gen algorithms, or performance budgets in depth — those are `atlas-3d-architect`, `atlas-world-designer`, and `atlas-performance-engineer` territory respectively.

---

## Findings

### 1. "True 3D conversion" has no tier home in the GDD as written
`docs/design/game_design_document.md` §1 defines the four tiers (MVP / Early Access / Full Vision / Experimental) entirely in terms of **simulation and AI depth** — offline heuristics vs. local LLMs vs. cloud DRL vs. decentralized swarms. Rendering technology is never used as a tier discriminator anywhere in that section. §8 ("Non-Negotiable Visual & Audio Requirements") specifies a *fully graphical, animated, polished* 2D hex strategy map — oceans, terrain variation, animated borders, weather particles, unit movement — and every one of those requirements is achievable in the existing Canvas 2D renderer or a straightforward WebGL swap. Nothing in the GDD text calls for or implies true 3D (camera tilt, extruded terrain, 3D models). A "true 3D conversion" is therefore an **addition to scope**, not a reinterpretation of an existing requirement, and currently has no GDD tier to attach to.

### 2. The renderer-swap seam is already the one true precedent, and it's explicitly non-3D-specific
`docs/architecture/technical_architecture.md` §3 and `docs/roadmap/milestone_roadmap.md` (Milestone 1 Architecture Requirements) both establish `WorldRenderer` as an interface with `CanvasWorldRenderer` (M1) and a reserved `'webgl'` factory branch — described as "a future WebGL implementation... swapped in without changes to the simulation engine, gameplay systems, save system, or UI logic." This is a 2D/2.5D-vs-WebGL seam already designed and committed (Milestone 1 is done, per the task brief). Any 3D work should be framed as *filling this exact seam* (`WebGLWorldRenderer` implementing the existing interface) — not as license to redesign the simulation/UI boundary. A "true 3D conversion" that touches anything outside `graphics/renderer/` would violate the architecture doc's own stated guarantee.

### 3. A "first playable 3D vertical slice" risks being read as re-scoping the whole roadmap
Milestones 2–6 (`milestone_roadmap.md`) are fully specified, sequential, and 2D-native (Perlin heightmaps rendered in 2D, diplomacy screen, action panels, Chronicle viewer, victory/collapse overlays) with no 3D dependency anywhere. A "vertical slice" for 3D should mean: one narrow path (e.g., render an existing `WorldSnapshot` through a new `WebGLWorldRenderer`, same camera/hex-picking contract, same placeholder assets via `AssetManager`) proven end-to-end — not a parallel bring-up of economy, politics, AI, or Chronicle systems in a 3D context. If any specialist's proposal implies redoing M2–M6 gameplay systems "in 3D," that is scope creep against the roadmap, not a vertical slice.

### 4. New-game flow has a canonical checklist already, and zero implementation exists yet
`docs/specifications/mvp_specification.md` §3 ("Game Setup & Initial Customization") is explicit and already ordered: (1) civilization count 4–8, (2) civilization selection/generation (preset or procedural, Name/Color/Faction Trait), (3) leader identity selection (player name + 2 traits; AI gets full procedural profile), (4) world seed (custom or random). I confirmed in `src/ui/App.tsx` that the current build renders `TopBar` + `WorldCanvasView` + `InspectorPanel` directly with **no setup/new-game screen at all** — the game currently boots straight into a world. So the "new-game flow" work is greenfield UI implementing an existing spec, not a redesign of an existing experience. Any proposal should be checked against this four-step list before adding steps (e.g., difficulty, map size, victory conditions) that aren't in the spec yet.

### 5. Campaign biographies must be a consumer of the existing Leader Profile schema, not a parallel one
`docs/specifications/civ_identity_ambitions_specification.md` already fully owns leader identity: 2 Major Traits, 1 Weakness, 1 Governing Priority, 1 Diplomatic Tendency, 1 Military Tendency, 1 Personal Ambition, 1 Fear, plus a Long-Term Ambition (§3) that can drift on capital loss, famine/bankruptcy, or succession (§5). `docs/specifications/world_chronicle_specification.md` §3 already establishes the intended pattern for turning structured data into prose — a `compileWarRecord`-style template function reading a structured JSON entry and interpolating it into narrative text. A "campaign biography" feature is structurally the same pattern applied to the Leader Profile object instead of a Chronicle event: read the existing trait/weakness/ambition/fear fields, template them into prose. It must not invent new trait vocabulary, a separate biography data model, or fields that duplicate what `civ_identity_ambitions_specification.md` already defines (e.g., a second "personality" system).

### 6. Precedent exists for correcting the GDD via addendum note, not silent edits
GDD §4 already contains a self-correcting parenthetical: "(Earlier drafts of this document referenced a 3-group subset; that version is obsolete — see `internal_politics_specification.md`.)" This is the established style for reconciling an old GDD statement with a newer authoritative spec. If 3D-conversion or new-game-flow work requires amending GDD tier definitions (see Finding 1), it should follow this same addendum pattern rather than a silent rewrite of §1.

## Recommendations

1. **Do not tier-place "true 3D conversion" as MVP work.** Treat it as exploratory/exhibit research adjacent to Full Vision/Experimental until the human Project Director explicitly decides where rendering technology sits in the tier system — the GDD currently has no axis for this decision, per Finding 1. Recommend the unified proposal ask the human this question directly rather than assume an answer.
2. **Constrain any 3D vertical-slice deliverable to the existing `WorldRenderer` contract.** It should be evaluated by whether it implements `WebGLWorldRenderer` against the current interface (`init`, `resize`, `renderFrame`, `hexAt`, `destroy`) using the same `WorldSnapshot`/`CameraState` types and `AssetManager` keys — not by how much of the game it visually reimagines. Anything requiring interface changes should be flagged as a breaking change to a shared contract per `MULTI_AGENT_WORKFLOW.md` §3 step 6, requiring sequential, reviewed work — not parallel implementation.
3. **Scope new-game flow strictly to `mvp_specification.md` §3's four steps first.** Additional setup options (difficulty, map size, house rules, etc.) should be called out as explicit additions beyond spec, not folded in silently, so the human approver can see they're extra scope.
4. **Campaign biography implementation should be a template/render layer only.** It reads `civ_identity_ambitions_specification.md` fields and (optionally) Chronicle history for a given leader, and produces prose — it should not add new leader attributes. If character-writer work surfaces a need for attributes the spec doesn't have (e.g., birthplace, dynasty name, age), that should be raised as a proposed *addition* to the civ-identity spec for explicit review, not assumed.
5. **If any specialist's proposal requires amending GDD §1's tier definitions** (e.g., to explicitly place rendering technology, or new-game-flow scope) **write it as an addendum note** in the style already used in §4, and cite the specific line being superseded.

## Contradictions or Disagreements Found

Per the workflow rules, specialists run in parallel and do not see each other's output before writing; `docs/architecture/reviews/` contained no other specialist files at the time this review was written, so I have **no actual conflicting recommendations to report** from other specialists' text. What follows are **structural overlap risks** visible from the role-assignment table in `docs/architecture/MULTI_AGENT_WORKFLOW.md` §1 that the Project Director should watch for when collecting the other six files:

1. **`atlas-ui-ux-designer`** is scoped to "new-game flow, civilization-selection **experience**" and **`atlas-civilization-designer`** is scoped to "civilization selection, custom creation, civilization **data structure**." Both role descriptions literally contain the phrase "civilization selection." The likely intended split is UX/flow/screen (ui-ux-designer) vs. data model/content (civilization-designer), but the wording overlaps enough that both specialists may propose an actual screen layout for the same step of the new-game flow. Recommend the Project Director explicitly confirm which one owns the civ-selection screen's visual/interaction design versus its underlying data contract.
2. **`atlas-3d-architect`** (renderer/vertical-slice scope) and **`atlas-performance-engineer`** (browser performance risk) are near-certain to interact: any 3D vertical slice proposal has direct performance-budget implications, and a performance-driven recommendation to stay in 2D/2.5D would directly contradict a 3D-architect recommendation to adopt WebGL/3D. This is not yet an observed contradiction, but it is the single highest-probability disagreement in this review round — flag for explicit reconciliation once both files exist.
3. **`atlas-character-writer`** (campaign biographies) and **`atlas-civilization-designer`** (custom civilization creation) may disagree on whether a fully player-customized civilization/leader should still receive a procedurally-generated biography, or whether custom leaders opt out of procedural narrative entirely. Not yet observed as a stated conflict, but the two features intersect at exactly this point.

## Open Questions for the Project Director

1. Should `docs/design/game_design_document.md` §1 be amended to add a rendering-technology axis to the tier definitions, given tiers are currently defined purely by simulation/AI depth? Without this, "true 3D conversion" cannot be honestly placed in MVP, EA, Full Vision, or Experimental.
2. Is the "first playable 3D vertical slice" intended to eventually *replace* `CanvasWorldRenderer` as the shipped default, or remain a parallel research spike proving the interface holds under a second implementation? This changes whether Milestone 1's already-committed, working build is at any risk of being superseded mid-roadmap.
3. Should new-game-flow implementation be pulled into Milestone 2 proper (which already scopes "Procedural Civilization Generator" and "Leader Generation Engine" per `milestone_roadmap.md`), rather than treated as a separately sequenced initiative? The spec content already lives there.
4. For campaign biographies: do AI-only leaders get biographies (as a Chronicle-adjacent feature, owned narratively by `atlas-character-writer`), or does the player's own leader also get a pre-game biography as part of new-game-flow leader identity selection (step 3 of `mvp_specification.md` §3, which would put it in `atlas-ui-ux-designer`/`atlas-civilization-designer` territory too)? This determines ownership and needs an explicit decision before implementation splitting.

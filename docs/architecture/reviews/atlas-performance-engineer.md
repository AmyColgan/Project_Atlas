# Atlas Performance Engineer — Review

Scope per `.claude/agents/atlas-performance-engineer.md`: quantify browser performance risk of the proposed 3D conversion, propose concrete/testable budgets for the first vertical slice, propose a profiling strategy, and define a fallback path. This is research/design only — no file outside `docs/` was touched. Grounded in `src/graphics/renderer/CanvasWorldRenderer.ts`, `src/graphics/renderer/WorldRenderer.ts`, `src/graphics/renderer/createRenderer.ts`, `src/graphics/camera.ts`, `docs/specifications/mvp_specification.md` (4–8 civs, up to 3 cities each, 40×40 grid), and `package.json` (current dependency set: `react`, `react-dom`, `zustand` only — zero 3D/WebGL dependencies today).

This review pressure-tests `atlas-3d-architect`'s specific proposal (Three.js used imperatively, `InstancedMesh` extruded hex prisms for the full 40×40 grid, one static-orbit camera, additive `CameraState` extension) — not "3D" as an abstract category. I read their file in full before writing this one.

## Performance Risk Assessment

**Baseline reality check.** The current `CanvasWorldRenderer` does one `fillRect`, one `translate`/`scale`, then per-tile `drawImage` + conditional `stroke()` calls inside a single `save()`/`restore()` pair, entirely on the CPU-composited 2D canvas path — no GPU context, no shader compilation, no draw-call concept in the WebGL sense. Its performance ceiling is "how fast can the browser rasterize ~1,600 small sprite blits," which is trivial on essentially any hardware built in the last decade. Any WebGL-based renderer is being compared against a baseline that is, for practical purposes, free. This is worth stating plainly because it means the question is never "is 3D fast enough in isolation" — it's "is the regression against a near-zero-cost baseline acceptable for what it buys visually." That framing drives every budget below.

**Draw calls — the architect's proposal is right, and the risk is real only if the implementation drifts from it.** A naive one-mesh-per-hex approach is ~1,600 draw calls/frame before city markers, borders, or hover/select are added — that would visibly stutter on integrated GPUs (mobile and laptop iGPUs typically start showing frame-time variance well before 1,000 unique draw calls, since each call carries fixed CPU-side driver overhead regardless of triangle count). `THREE.InstancedMesh` collapses this to effectively one draw call for all 1,600 terrain prisms, which is the correct mitigation and I have no disagreement with it. The risk is entirely in execution discipline: every additional visual layer (borders, hover outline, selection outline, city markers) needs to independently commit to instancing or a shader-based technique, or the draw-call count creeps back up one layer at a time. This is exactly the failure mode the architect's own "Border/selection overlays" risk note anticipates — I'm confirming it, not discovering it independently.

**Border/selection overlays are the layer most likely to silently blow the draw-call budget.** The current Canvas 2D renderer strokes borders and hover/select outlines essentially for free (`ctx.stroke()` on an already-open path). A 3D reimplementation that draws a separate line-loop mesh per bordered tile (plausible — up to ~1,600 tiles could have an owner) reintroduces exactly the draw-call problem instancing was meant to solve, just on a different mesh. This must be either (a) a single instanced mesh of border-segment quads keyed by per-instance owner-color, or (b) a fragment-shader edge-detection pass over a border-mask texture. Either is fine; "one mesh per bordered tile" is not, and should be treated as a design-review gate before merge, not caught in post-hoc profiling.

**City markers are not a real risk at this scale.** Even without instancing, up to 24 cities (8 civs × 3 cities max per `mvp_specification.md` §1) is a trivial draw-call count on any GPU from the last 15 years. Instancing city markers is nice-to-have polish, not a budget-relevant concern — flagging so effort isn't misallocated here at the expense of the border-overlay problem above, which is the real risk.

**Bundle size / startup cost is a real, unavoidable regression.** `package.json` currently ships zero 3D dependencies; the architect's own estimate is ~150–180KB min+gzip for Three.js core (scene/camera/renderer/geometry, tree-shaken). That number assumes disciplined imports — no `GLTFLoader`, no `postprocessing`, no example addons pulled in wholesale, which is easy to violate incrementally once Three.js is in the dependency graph and a later milestone wants a post-processing bloom effect or a loaded model. I'm treating 150–180KB as a floor, not a ceiling, for the vertical slice's actual delta.

**Shader compilation is a new, non-negotiable first-frame stall class.** Canvas 2D has no equivalent to this. `THREE.WebGLRenderer`'s first `render()` call compiles and links shader programs synchronously on the main thread the first time each unique material is used; on a mid/low-end GPU this can be tens to a couple hundred milliseconds, and it is characteristically worse on mobile GPU drivers than desktop. For a scene with a handful of materials (terrain, border, city marker, hover/select highlight) this should be small, but it is non-zero and must be measured, not assumed away — it's exactly the kind of regression that looks fine on a development desktop and is very visible on the reference low-end hardware defined below.

**Mobile/low-end integrated GPU is genuinely new failure-mode surface, not just a slower version of desktop.** Context creation can fail outright (WebGL2 unsupported or disabled, common on older Android WebViews and some locked-down enterprise/school Chromebooks), and contexts can be lost and never restored under memory pressure — `webglcontextlost`/`webglcontextrestored` handling is mandatory, matching the architect's note. Canvas 2D has no equivalent failure mode at all; this is pure new risk surface, not a tradeoff, and it must be handled with a fallback (see Fallback Strategy), not just logged.

**No platform/device target is specified anywhere I could find.** `mvp_specification.md` does not name a minimum device tier, mobile support, or browser support matrix, and neither does `docs/architecture/technical_architecture.md`. The budgets below therefore assume a reasonable desktop-first-but-mobile-web-tolerant range in the absence of other guidance — this is flagged explicitly as an open question below rather than silently decided.

## Proposed Budgets

All budgets are for the **vertical slice scope as defined by `atlas-3d-architect`**: full 40×40 grid (1,600 tiles) via `InstancedMesh`, borders, hover/select, up to 24 city markers, one static-orbit camera, one directional + one ambient light, flat-color/simple-procedural materials — no LOD, no heightmap mesh, no unit/army models, no weather.

**Reference hardware (proposed, needs Project Director / stakeholder sign-off since no target is specified in the spec):**
- **Tier A (target, "should feel like M1"):** a 2020–2022 mid-range laptop with integrated graphics (e.g. Intel Iris Xe / UHD 620 class) running Chrome, no discrete GPU.
- **Tier B (floor, "must not be broken"):** a mid-tier Android phone from the same era (e.g. Adreno 610/612 or Mali-G52 class SoC, ~$250–300 retail at launch) running Chrome for Android.
- Desktop with a discrete GPU is assumed to clear both tiers trivially and is not a separate gate.

**Frame rate:**
- Tier A: **60fps sustained** (frame time ≤16.6ms, p95 ≤18ms) during static-orbit viewing and during hover/select/border-pulse animation.
- Tier B: **≥30fps sustained** (frame time ≤33ms, p95 ≤40ms) under the same conditions. This is the hard floor — below this, the slice does not meet budget on the low-end reference and the fallback path (below) governs.

**Draw calls per frame (measured via `renderer.info.render.calls`):**
- Terrain (all 1,600 hexes): **≤ 2** (one `InstancedMesh` for prisms; a second only if top/side faces need separate materials).
- Borders (all owned tiles, worst case ~1,600): **≤ 3** (instanced or shader-based per the risk note above).
- Hover + selection outlines: **≤ 2**.
- City markers (≤24): **≤ 2** (instanced; a non-instanced fallback of ≤24 individual draw calls is tolerable given the low count, per the risk assessment above, but instancing is preferred for consistency).
- **Total budget: ≤ 12 draw calls/frame**, hard ceiling **20**. Anything crossing 20 on this scene composition is a signal the border-overlay risk above has materialized and needs redesign, not tuning.

**Bundle size:**
- Max **+220KB min+gzip** delta to the production bundle for the WebGL path (Three.js core + the vertical slice's own renderer code), enforced by a CI size-check (see Profiling & Testing Strategy). This gives ~40KB of headroom over the architect's own 150–180KB estimate for the renderer code itself, not for scope creep (loaders, postprocessing, extra example addons must not land inside this budget without an explicit re-review).
- If `CanvasWorldRenderer` remains the shipped default (recommended — see Fallback Strategy), this delta should ideally be **code-split** so users who never opt into 3D never download it. Flagged as an implementation requirement, not optional polish, since it's the difference between "regression for everyone" and "regression only for 3D users."

**Load time / startup:**
- **≤300ms** added to time-to-interactive on Tier A versus the current Canvas 2D baseline, measured end-to-end (script download+parse+execute+first `renderFrame` call returning), when the WebGL path is chosen.
- **First-3D-frame stall** (time from `WorldRenderer.init()` call to first completed `renderFrame()`, which is where shader compilation cost lands): **≤150ms** on Tier A, **≤400ms** on Tier B. This is measured separately from general TTI because it's the one cost class Canvas 2D structurally cannot have, and it's the most likely place a "feels fine on desktop, stutters on phone" surprise appears.

**Memory:**
- **≤50MB** GPU texture memory for the vertical slice (flat-color materials / simple procedural textures per the architect's asset plan should make this generous headroom, not a tight constraint — if texture memory approaches this, materials have drifted from "flat color" toward "real textures" and that's worth flagging).
- **≤150MB** total GPU buffer allocation (geometry + instance attribute buffers + textures combined) for the full 1,600-tile scene.
- **No per-frame heap allocation in the render loop** — `renderFrame()` must not allocate new arrays/objects per call (a common source of GC-pause frame drops that would be invisible in a synthetic single-frame benchmark but visible as periodic stutter over a play session). Verify via Chrome DevTools Memory panel's allocation-over-time view during a multi-minute idle-orbit session, not just a single frame capture.

## Profiling & Testing Strategy

**Instrumentation to add (in `graphics/` only, per the ground rule against touching other code):**
- Wrap each `renderFrame()` call with `performance.now()` timing, keep a rolling buffer (e.g. last 300 frames), and expose p50/p95/p99 frame time — not just an average, which hides exactly the stutter this review is worried about. This can live as a debug overlay or a console-loggable diagnostic behind a flag; it does not need to ship in production UI.
- Read and log `renderer.info.render.calls`, `renderer.info.render.triangles`, and `renderer.info.memory.{geometries,textures}` (all built into `THREE.WebGLRenderer`) at the same cadence — this directly measures the draw-call and memory budgets above without guesswork.

**Tools, mapped to what each measures:**
- **Chrome DevTools Performance panel** (main-thread flame chart + GPU track): first-3D-frame shader-compile stall, and whether frame drops are CPU-bound (JS/driver overhead) or GPU-bound (fill rate/shader cost) — this distinction determines whether instancing or material simplification is the right fix if a budget is missed.
- **Chrome DevTools Rendering tab** → paint flashing / frame rendering stats, plus CPU/GPU throttling (4x/6x CPU slowdown, GPU throttle) as a cheap proxy for Tier B when a physical low-end device isn't on hand during day-to-day development — physical-device verification (see below) is still required before sign-off, throttling is for iteration speed only.
- **Lighthouse** (CI-integrated): bundle size, time-to-interactive, total blocking time — catches bundle/load-time budget regressions automatically on every PR touching `graphics/`.
- **`renderer.info.*` + custom `performance.now()` overlay** (above): draw calls, triangle count, frame-time percentiles — the day-to-day numbers an engineer watches while iterating on the renderer itself.
- **A scripted headless perf check** (Playwright, since browser automation is already a reasonable fit for this repo's testing needs): load the vertical slice, force N seconds of the static-orbit camera plus a scripted hover/select/pan sequence, capture frame-time percentiles and `renderer.info` counters, and fail CI if Tier-A-equivalent throttled numbers exceed budget. This is the only way these budgets stay enforced rather than becoming a one-time manual check that bit-rots.
- **Physical device pass**, not throttling-only: at least one real Tier B device (or a cloud device lab / BrowserStack-equivalent session) before the vertical slice is marked done. Integrated-GPU driver behavior (especially shader compile time and context-loss frequency) does not reliably reproduce under desktop throttling — this is a known gap between synthetic and real low-end hardware and should not be skipped to save time.

**When to run each check:**
- Frame-time/draw-call instrumentation: continuously during `WebGLWorldRenderer` development, checked by the implementing engineer before every commit touching it.
- Lighthouse + scripted Playwright perf check: on every PR touching `graphics/renderer/` or `graphics/assets/`, gating merge.
- Physical Tier B device pass: once, before the vertical slice is declared "done" per the architect's definition-of-done, and again before any later milestone that changes materials/lighting/geometry complexity in a way that could regress it.
- Bundle size CI check: on every PR that touches `package.json` dependencies or `graphics/renderer/` — this is the cheapest possible check and should run on every commit, not just before milestone sign-off.

## Fallback Strategy

**Canvas 2D remains the shipped default; this is a strong recommendation, not a hedge.** `createRenderer.ts`'s `case "webgl"` is already stubbed as "not implemented yet" with `canvas2d` as the only working path today — I recommend this stay the *default* case even after `WebGLWorldRenderer` exists, echoing the architect's own Open Question 2 and the game-director's Finding 1 (3D currently has no home in any GDD tier). Concretely: **do not flip the default in `createRenderer` until a human Project Director explicitly approves it**, given it's currently ungated exploratory work.

**The renderer abstraction already makes this fallback nearly free — that's the main finding of this section.** Because `WorldRenderer` is a plain interface and `createRenderer(kind: RendererKind)` is the single selection point, "3D risks missing budget on this device" reduces to a runtime `kind` decision, not an architecture problem:
1. **Capability probe before instantiation**, living in app-level code (not inside either renderer, keeping the interface clean per the architect's design): attempt a throwaway `canvas.getContext('webgl2')`; if it returns `null`, or a synthetic one-frame render exceeds a time threshold, or `navigator.hardwareConcurrency`/`deviceMemory` (where available) suggest low-end hardware, choose `"canvas2d"`.
2. **Context-loss recovery, not just detection.** On `webglcontextlost` with no `webglcontextrestored` within a short grace period (a few seconds), tear down `WebGLWorldRenderer` via its existing `destroy()` and re-`init()` a fresh `CanvasWorldRenderer` in its place. Because both renderers satisfy the same interface and consume the same `WorldSnapshot`/`CameraState`, this swap is a call-site decision, not a re-architecture — this is the direct payoff of the architect's "no interface changes" design and worth stating plainly as a benefit, not just a risk mitigation.
3. **No graduated LOD/quality-tier system for the vertical slice.** A multi-tier quality system (reduced draw distance, simplified shaders, etc.) is real engineering effort and is explicitly out of scope per the architect's own vertical-slice exclusions ("LOD systems" is on their out-of-scope list) — I agree with that scoping. The fallback for "3D doesn't meet budget on this device" is binary (drop to Canvas 2D entirely), not graduated, for this slice. A quality-tier system only becomes worth proposing if 3D is approved beyond the vertical slice into an actual shipped feature.
4. **This binary fallback is only as good as the probe's accuracy** — a capability/heuristic probe can produce false positives (a device probes as "should be fine" but isn't) or false negatives (a device that could handle it gets routed to Canvas 2D unnecessarily). The Playwright/Lighthouse-based budget checks above catch regressions in CI; they do not catch a bad probe heuristic in the field. If 3D ships beyond the vertical slice, the probe itself should be revisited once real device telemetry exists — noted here so it isn't assumed solved by the CI checks alone.

## Contradictions or Disagreements Found

1. **No contradiction with `atlas-3d-architect`'s technical approach.** Three.js + `InstancedMesh` for the terrain layer is the correct mitigation for the single biggest risk (draw calls), and I have no disagreement with the technology or instancing recommendation itself. Both the game-director's review (Contradictions §2) and the architect's own review predicted a performance-engineer/3D-architect clash as "the single highest-probability disagreement in this review round" — having now written both budgets, I don't think that clash actually materializes at the *architecture* level; it resurfaces below at the *tier/approval* level instead.
2. **Real, unresolved tension: whether this budget is achievable is an empirical question, not one either of us can settle from a design document alone.** The architect's proposal is well-designed *if* implemented with discipline (instancing on every layer, no scope creep on materials/loaders). Whether it actually lands inside the frame-time and load-time budgets above on genuine Tier B hardware cannot be known until `WebGLWorldRenderer` is built and profiled — this review supplies the numbers to test against, it does not certify the proposal passes them in advance. Recommend the vertical slice's "definition of done" (already written by the architect to depend on "whatever budget performance-engineer sets") be read as *provisional pass* pending the physical-device profiling pass described above, not as a foregone conclusion.
3. **Agree with the game-director's Finding 1 and the architect's Open Question 1**: since the GDD places no tier on rendering technology, and the MVP spec (`mvp_specification.md` §2) already permits either "HTML5 Canvas API... or WebGL" for the *existing* 2D-style visual requirements, a budget-driven reading of the spec does not require true 3D (camera tilt, extruded geometry) to satisfy the MVP tier at all — a WebGL renderer could satisfy §2's letter while staying visually 2D/2.5D (flat sprites, orthographic camera) at a fraction of this review's risk profile. I'm not recommending that instead of true 3D — that call belongs to the Project Director per the architect's own deferral — but flagging that "3D" and "WebGL" are being used interchangeably across the other specialists' reviews and they are not the same performance question. A WebGL-but-still-2D-style renderer would clear nearly every budget above trivially; the true-3D camera/extruded-prism approach is the one this review's actual risk numbers are about.
4. **No conflict found with `atlas-world-designer`'s proposal** (optional `elevation?`/`moisture?` fields on `HexTile`) — this is additive data, not a rendering decision, and doesn't change any budget above regardless of whether it's approved.
5. **Minor note on the architect's file, not a disagreement:** their claim that "instancing makes the full grid roughly the same cost as a handful" is true for draw-call count specifically, but not automatically true for fill-rate/overdraw or CPU-side per-instance attribute updates (e.g. if border-pulse or hover-highlight state requires updating per-instance attributes every frame for a subset of 1,600 instances, that update cost scales with tile count even though the draw call doesn't). Worth empirical verification during profiling rather than treating "instancing = free" as settled.

## Open Questions for the Project Director

1. **No device/platform target exists in `mvp_specification.md` or `technical_architecture.md`.** Is mobile-web support even an MVP goal? The Tier A/Tier B reference hardware above is my best guess absent other guidance — if mobile is explicitly out of scope for MVP, the Tier B floor (and much of the mobile-specific risk in this review) can be relaxed or deferred.
2. **Should the ≤220KB gzip bundle budget be a hard CI-enforced gate (build fails over budget) or a soft warning?** I recommend hard-gated given how easily Three.js dependency creep happens once it's in the graph, but this has workflow implications (blocks merges) worth the Project Director's explicit sign-off rather than assuming enforcement level.
3. **Per Contradictions §3 above: is "true 3D" (tilted camera, extruded geometry) actually required for the MVP tier, or would a WebGL-but-visually-2D renderer satisfy `mvp_specification.md` §2's letter at substantially lower performance risk?** This is the same tier-placement question the architect and game-director both already raised from their own angles; I'm adding that it has a large, quantifiable performance-cost difference, not just a scope/fidelity one.
4. **Does the vertical slice's "definition of done" require passing physical Tier B device testing, or is throttled-desktop-only verification acceptable for a first slice?** I recommend requiring the physical pass (driver-level shader compile/context-loss behavior doesn't reliably reproduce under throttling), but this adds real time/logistics (device access) to the slice timeline, which is a scheduling call, not a technical one.
5. **Should `CanvasWorldRenderer` be guaranteed to stay maintained long-term as a permanent fallback (my recommendation), or is it acceptable for it to bit-rot once/if a 3D path ships?** This directly determines how much ongoing engineering cost the fallback strategy above actually costs versus a one-time build.
